# 复盘记录

用这个文件把重复出现的 agent 错误沉淀成长期规则。

## 重复失败

### 失败项

出了什么问题：
回答「这个项目是干嘛的」时，只读了 `USER_BRIEF.md` 和过时的 `docs/PROJECT_CONTEXT.md`，就据此断言前端是 Streamlit、角色是 Researcher/Critic/Synthesizer，并在用户提醒后才发现真实代码（Next.js 前端 + 名人顾问）与文档严重不符。

根因：
文档（`PROJECT_CONTEXT.md`、`DECISIONS.md`）停留在原始设计阶段，未随架构演进更新；而 agent 把文档当作真相，未先核对真实目录与代码文件。

新增规则：
1. 回答关于项目形态、架构、技术栈的问题时，必须先看真实的目录结构（`list_dir`）与关键源码（入口、package.json、路由），不能只信 `USER_BRIEF.md` 或既有文档。
2. 若发现文档与代码不一致，以代码为准，并同步更新 `docs/` 下相关文件。
3. `docs/` 是易过时信息，阅读时标注其可能滞后；重大项目改动后应主动回写文档。

新增验证：
- 使用「项目是干嘛的 / 技术栈 / 架构」类提问时，验证是否已检查真实文件，而非仅引述文档。

### 失败项

出了什么问题：
未能识别 `backend/`（FastAPI）与 `engines/`（LangGraph/AutoGen）是遗留代码，未确认前端实际请求路径（实际只调 `/api/chat/advisor`）。

根因：
依赖命名（backend/engines 显得重要）而未通过代码引用关系（grep 前端是否 import backend / 调 localhost）确认真实活跃路径。

新增规则：
判断代码是否「活跃」要看引用关系，而非目录名或是否被文档提及。用 grep 确认前端是否 import / fetch 到该模块。

新增验证：
- 报告模块职责前，grep 该模块是否被其他活跃代码引用。

## 有效模式

### 模式

什么做法有效：
以「文档 + 目录结构 + 关键源码交叉核对」的方式，最终得到与代码一致的项目认知。

适合在哪里复用：
任何需要先理解代码库再行动或回答的场景；多文件大改动前先完整盘点真实结构。
